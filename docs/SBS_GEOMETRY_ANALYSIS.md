# RayNeo Air 3s：SBS 虚拟银幕的几何模型与修改设计

分析日期：2026-09-05。代码基线：`ea17589`，结合当前工作区读取；保留已有未提交修改。

本文目标是用户确认的「普通 2D 视频显示为具有可调远近感的虚拟银幕」。第 1–13 节保留升级前的代码分析、数学推导、参数依据与设计；其中“当前代码”指上述分析基线。初次实现及桌面验收见第 14 节；真机排查与佩戴结果见第 15 节。**第 15 节的 XR 空间服务方案已废弃，当前独立 USB 实现在第 16 节。** 以下“距离”默认指双眼会聚刺激指定的距离，不保证等于每个人主观报告的距离。

## 1. 结论与证据边界

**当前 SBS 已经有左右眼打包逻辑，但没有应用生成的双目视差。** 它足以把同一帧送入两眼，尚不足以相对于镜像 2D 改变虚拟银幕的深度。用户的判断符合代码证据。

对正对用户、没有倾斜的平面银幕，满足目标不需要第二个播放器，也不需要逐像素深度估计：同一帧纹理可以复用，左右眼使用不同的投影位置即可。关键工程关系为：

\[
d=f_x b\left(\frac{1}{Z}-\frac{1}{Z_0}\right),\qquad
\Delta u_L=+\frac d2,\quad\Delta u_R=-\frac d2.
\]

这里的视差 `d` 是**单眼局部坐标中对应点的横坐标差**，不是整个 SBS 帧中两幅图之间相隔的半屏宽度。公式成立的坐标、校准及近似条件见第 4–6 节。

还不能仅凭代码确认用户设备已成功进入 SBS：硬件命令确认、实际输出尺寸、两眼通道映射和视频纹理是否重放成功，都必须在设备上检查。缺少视差是确定的实现缺口；硬件通路是否还有问题是独立的待验证项。

## 2. 当前项目究竟画了什么

### 2.1 绘制链

入口为 `AndroidApp/app/src/main/java/com/jellyfinforrayneo/client/GlassesWebViewController.java`：

- `applyDisplayState()`，约 267 行：只有 `displayModeApplied=true` 且 `activeMode=stereo_screen` 才启用 SBS；切换失败仍可能显示 Mirror 2D。
- `StereoMirrorLayout.onMeasure()`，约 513 行：把唯一 WebView 测量为容器宽度的一半。
- `onLayout()`，约 525 行：WebView 仍在 `(0, 0)` 布局。
- `dispatchDraw()`，约 537 行：左眼绘制一次；右眼仅 `translate(eyeWidth, 0)` 后再绘制同一子 View。

设整个容器宽度为 `2W`，原始帧为 `I(x,y)`，理想化表示当前输出：

\[
F(x,y)=
\begin{cases}
I(x,y),&0\leq x<W,\\
I(x-W,y),&W\leq x<2W.
\end{cases}
\]

硬件按左右半屏分流后：

\[
I_L(u,v)=I_R(u,v)=I(u,v),\qquad d(u,v)=0.
\]

`translate(W,0)` 只把右眼图放进传输帧的右半区；减掉右眼区原点 `W` 后，其眼内位置仍与左眼完全相同。

镜像 2D 同样向双眼提供相同图像。在通道映射、单眼视场、比例和时序一致的前提下，这两条通路给出的双目几何线索相同。不能从 `d=0` 推断“没有光学虚像”或“一定在无穷远”；它表示停留在设备与佩戴共同决定的零视差基准。

### 2.2 硬件 API 不会自动生成深度

`RayNeoDisplayController.java` 约 211 行调用 `AirApi.switchTo3DMode()`。已对项目固定的官方 Air SDK 1.0.3 下载包核验 MD5，并以 `javap -c` 检查其 AAR：

```text
AirApi.switchTo3DMode() -> ArcheryDevice.enableSideBySideMode()
AirApi.switchTo2DMode() -> ArcheryDevice.disableSideBySideMode()
```

这段 API 调用不接收银幕距离、眼间距或图像投影矩阵。应用仍需生成左右眼图像。官方 SDK 的双目相机、瞳距与视场配置属于另外的渲染流程，不能期待仅调用分流命令就获得那些效果。[R2][R4]

### 2.3 当前命名与能力有偏差

`DisplayModeStateMachine.successMessage()` 约 190 行明确描述“同一 WebView 帧正在左右眼重放”；手机端却称之为“立体屏幕 / SBS 空间画面”，使用指南也声称形成立体虚拟屏幕。这会把“已左右分流”与“已经设置银幕深度”混为一谈。实施后应以实际能力更新这些文案。

`RayNeoDisplayController.onSensorChanged()` 约 42 行忽略姿态数据，因此当前是**随头移动的银幕**。仅增加视差也不会让银幕固定在房间中；世界固定与头部追踪是另一项功能。

### 3.2 建模用的标称参数

以下是计算假设，不能替代测量：

```text
每眼参考栅格：N = 1920，M = 1080
纵横比：16:9，方形像素，近似无畸变
46° 暂按对角视场解释
眼间距 b = 0.064 m：仅为数值算例，不是用户测量值
```

与此一致的一对一 Full-SBS 目标是 `3840×1080`。这个目标来自两份 `1920×1080` 的横向拼接，**不是已经测到的当前 Android 显示模式**。运行时必须读取实际 Display 模式、Presentation/View 尺寸及映射。

46° 按对角视场解释的合理性可以做数量级校验：201 英寸对角线为 `5.1054 m`，若把它放在等效距离 `6 m`：

\[
2\arctan\frac{5.1054}{2\times6}\approx46.095^\circ.
\]

反过来，201 英寸与 46° 对应约 6.014 m 的**角尺寸等效距离**。这说明该假设几何上自洽，不证明零视差会聚距离或光学焦距就是 6 m。

### 3.3 必须保留为未知或可校准的量

- 用户有效眼间距 `b`，以及实际佩戴后的左右眼位置。
- 零软件视差对应的会聚距离 `Z0`，包括它可能接近无穷远的情况。
- 光学调焦距离 `Za`，以及处方镜片对调焦刺激的影响。
- 左右眼的像素到出射光线映射、主点、畸变和垂直配准误差。
- 3D 模式实际分辨率、刷新率、眼序、旋转、缩放和有效可视区。

官方公开网页没有提供足以解出这些量的完整 Air 3s 光学标定数据。**只知道 FOV 和分辨率，无法唯一求出绝对观看距离。**

## 4. 坐标与数学符号

采用头部坐标：`X` 向右，`Y` 向上，`Z` 向前；眼睛中心位于：

\[
E_L=(-b/2,0,0),\qquad E_R=(b/2,0,0).
\]

| 符号 | 含义 | 单位 |
| --- | --- | --- |
| `b` | 眼间距，投影基线 | m |
| `Z` | 目标银幕中心的会聚距离 | m |
| `Z0` | 相同眼内像素对应的零视差基准距离 | m |
| `Za` | 光学调焦距离，独立于 `Z0` | m |
| `N,M` | 标定坐标中的单眼宽、高 | px |
| `uL,uR` | 对应点的单眼局部水平像素坐标，向右为正 | px |
| `d=uL-uR` | 本文使用的总视差 | px |
| `fx,fy` | 将光线斜率换算到像素的有效焦距 | px |
| `s` | 银幕相对单眼有效区域的等比尺寸比例 | 无量纲 |
| `V=1/Z` | 会聚距离倒数；不是棱镜度 | m⁻¹ |

全帧坐标中左眼原点为 0，右眼原点为 `N`，所以：

\[
d=x_L^{packed}-(x_R^{packed}-N).
\]

SBS 半屏间距 `N` 不应加入几何视差。

## 5. 由 Air 3s 标称视场求像素尺度

在对称针孔、方形像素模型下，设对角视场 `φd=46°`：

\[
f_x=f_y=f=\frac{\sqrt{N^2+M^2}}{2\tan(\varphi_d/2)}.
\]

\[
\varphi_h=2\arctan\frac{N}{2f},\qquad
\varphi_v=2\arctan\frac{M}{2f}.
\]

代入 `1920×1080`：

\[
f\approx2594.862\ \mathrm{px},\quad
\varphi_h\approx40.605^\circ,\quad
\varphi_v\approx23.511^\circ.
\]

不能把 46° 直接当水平 FOV 再计算 `fx`；这样会引入约 13% 的尺度差异。若后续得到官方明确的水平/垂直参数，应替换当前假设。

中心附近一像素对应的角度约为：

\[
\delta\theta\approx1/f=0.0003854\ \mathrm{rad}
\approx0.02208^\circ=1.325\ \mathrm{arcmin}.
\]

中心约 `45.289 px/degree`；全视场平均 `N/φh≈47.285 px/degree`。二者不同，因为 `u=f tan(θ)` 非线性，不能把广告中的 PPD 无条件当作全屏统一换算常数。

## 6. 从双目光线推导视差与距离

### 6.1 经校正的平行投影模型

先采用左右眼共用朝向、焦距相同、畸变已校正的投影坐标。用主点偏移表征零视差基准。对点 `P=(X,Y,Z)`：

\[
u_L=c_x+f_x\frac{X+b/2}{Z}-\frac{f_xb}{2Z_0},
\]

\[
u_R=c_x+f_x\frac{X-b/2}{Z}+\frac{f_xb}{2Z_0}.
\]

纵坐标采用屏幕向下为正：

\[
v_L=v_R=c_y-f_y\frac{Y}{Z}.
\]

两式相减、相加，得到：

\[
\boxed{d=f_xb\left(\frac1Z-\frac1{Z_0}\right)}\tag{1}
\]

\[
\boxed{\bar u=\frac{u_L+u_R}{2}=c_x+f_x\frac XZ.}\tag{2}
\]

式 (1) 控制会聚，式 (2) 控制双眼平均方向。对称移动使银幕前后变化时不会同时向左或向右漂移。

反解距离：

\[
\boxed{Z=\frac1{1/Z_0+d/(f_xb)}}.\tag{3}
\]

因此，按照本定义且眼序已确认：

- `d>0`：左眼画面右移，右眼画面左移，会聚增加，银幕相对基准变近。
- `d=0`：回到 `Z0`，对应当前 SBS 的几何状态。
- `d<0`：会聚减少，相对基准变远。
- `d=-fx b/Z0`：两条中心光线平行，目标在无穷远。
- `d<-fx b/Z0`：光线向外发散，不对应眼前有限的正常银幕，应排除。

有些文献使用 `uR-uL`，符号会完全相反。实现与验收必须固定一种定义，不能只写“正视差”而不写方向。

### 6.2 平面银幕为什么只需要统一平移

令整块银幕处于 `Z=Zs`，则所有点的 `d` 都一样。对同一纹理采用相同缩放后，分别加 `+d/2` 与 `-d/2`，正好得到这个正对用户的平面的两个投影。

这为当前项目提供了一个重要的最小实现：**复用同一帧是正确的；缺少的是左右眼不同的变换。** 不需要为这个目标生成两个内容不同的视频流。

物体内部若需要前后层次，必须有 `Z(X,Y)`，视差才会随内容位置变化。本次普通 2D 片源没有这些信息，统一偏移只改变承载影片的平面，影片内人物不会因此获得新的双目体积。

### 6.3 会聚角与中心的精确角度模型

中心目标的几何会聚角为：

\[
\beta(Z)=2\arctan\frac b{2Z}.
\]

如果设备是左右光轴分别朝内旋转 `α0=atan(b/(2Z0))` 的对称针孔系统，则中心点所需偏移的精确公式是：

\[
d_{angle}=2f_x\tan\left(\arctan\frac b{2Z}-\arctan\frac b{2Z_0}\right)
=\frac{f_xb(1/Z-1/Z_0)}{1+b^2/(4ZZ_0)}.\tag{4}
\]

式 (1) 对经校正的平行投影模型是精确的；对这里的旋转光轴中心模型则是一阶近似。`b=64 mm, Z0=6 m, Z=2 m` 时，两者仅差约 `0.0047 px`。实际未知的佩戴与光学映射误差通常更值得优先测量。

但式 (4) 只验证中心角度。实际旋转光轴或存在畸变时，整屏边缘不一定能靠统一平移完全校正，不能由中心近似误差小就宣称全屏光学精确。

### 6.4 完整设备模型的形式

对每只眼，用经标定的函数 `g_e(u,v)` 把最终显示像素映射成头部坐标中的单位光线。可用以下模型或查找表描述它：

\[
\hat r_e(u,v)=\operatorname{normalize}\left(R_eK_e^{-1}
\widetilde{\mathcal U_e(u,v)}\right).
\]

`Ke` 是有效投影内参，`Re` 是光轴朝向，`𝒰e` 是去畸变映射，波浪线表示齐次坐标。真实系统中这些量还可能依赖眼睛在 EyeBox 中的位置。

对于目标点 `P`，求各眼像素使：

\[
\hat r_e(u_e,v_e)\parallel P-E_e.
\]

对观测像素，可通过最小化两条光线的距离进行三角化：

\[
\min_{t_L,t_R>0}\left\|E_L+t_L\hat r_L-E_R-t_R\hat r_R\right\|^2.
\]

两条光线最近点的中点给出估计位置，残差可用于检测垂直错位或模型失配。这是更一般的数学定义；第 6.1 节是它在理想平面银幕条件下的简化。没有 `gL,gR` 标定数据时，不应将简化模型输出标为“实测距离”。

## 7. 数值算例与误差

下表**假设** `b=64 mm, fx=2594.862 px, Z0=6 m`。`Z0=6 m` 只为了展示计算，不是 Air 3s 已知光学事实。正方向均为单眼图像向右。

| 目标会聚距离 Z | 总视差 d | 左眼偏移 | 右眼偏移 | 相对基准会聚角变化 |
| ---: | ---: | ---: | ---: | ---: |
| 2 m | +55.36 px | +27.68 px | −27.68 px | +1.222° |
| 2.5 m | +38.75 px | +19.37 px | −19.37 px | +0.856° |
| 3 m | +27.68 px | +13.84 px | −13.84 px | +0.611° |
| 4 m | +13.84 px | +6.92 px | −6.92 px | +0.306° |
| 6 m | 0 px | 0 px | 0 px | 0° |
| 10 m | −11.07 px | −5.54 px | +5.54 px | −0.244° |
| 无穷远 | −27.68 px | −13.84 px | +13.84 px | −0.611° |

`fx b≈166.071 px·m`。每增加 `0.1 m⁻¹` 的会聚需求，总视差增加约 `16.61 px`；这是使用距离倒数控制滑杆的依据。

如果错误地把零基准设为无穷远，公式会变成 `d=fx b/Z`。例如 3 m 要用 `55.36 px`；而基准实际为 6 m 时只需 `27.68 px`。**遗漏基准项会产生系统误差，不能仅凭 `d=fb/Z` 就写死偏移。**

距离误差对视差误差的敏感性：

\[
\frac{\partial Z}{\partial d}=-\frac{Z^2}{f_xb},\qquad
\sigma_Z\approx\frac{Z^2}{f_xb}\sigma_d.
\]

一像素总视差误差分别约对应：3 m 处 `0.054 m`、6 m 处 `0.217 m`、10 m 处 `0.602 m`。越远越不适合显示过多小数位。

用距离倒数表示完整的一阶误差传播更清楚。设 `V0=1/Z0`：

\[
\delta V\approx\delta V_0+\frac{\delta d}{f_xb}
-(V-V_0)\left(\frac{\delta f_x}{f_x}+\frac{\delta b}{b}\right).
\]

既要保留浮点亚像素平移，也要承认 `b`、`fx` 和基准误差；不能靠给输出距离增加小数位制造精度。

## 8. 银幕尺寸、距离与裁剪必须一起设计

### 8.1 视差与缩放控制不同的量

设银幕实际几何宽高为 `Ws,Hs`，其中心距为 `Zs`。中心视点看到的水平角宽为：

\[
\theta_s=2\arctan\frac{W_s}{2Z_s}.
\]

在参考单眼栅格中，它应占据的宽度与比例为：

\[
w_s=f_x\frac{W_s}{Z_s},\quad
s=\frac{w_s}{N}=\frac{W_s}{2Z_s\tan(\varphi_h/2)}.
\]

因此有两种合理交互：

| 交互 | 改变距离时的尺寸行为 | 用途 |
| --- | --- | --- |
| 保持角尺寸 | `s` 不变，隐含 `Ws∝Zs` | 单独验证视差，或让用户独立调节“远近”和“大小” |
| 保持物理尺寸 | `Ws` 不变，`s∝1/Zs` | 模拟一块固定尺寸银幕被拉近或推远 |

如果只缩小左右相同的图像、仍令 `d=0`，改变的是角尺寸，双目几何深度仍为 `Z0`。反过来，改变视差不一定需要缩小画面；缩小通常是为了保留边界或模拟固定物理尺寸。

标称满视场在 `Z=6 m` 时相当于约 `200.54 英寸` 对角线；在 `Z=3 m` 时只相当于约 `100.27 英寸`。若在 3 m 处使用 `s=0.9`，几何等效约 `90.24 英寸`。不能在任意距离仍声称“201 英寸且完整可见”。

### 8.2 完整绘制矩阵

先考虑输出一比一对应单眼栅格，源 WebView 为 `N×M`。同一源点 `(x,y)` 的两眼位置为：

\[
u_e=s(x-N/2)+N/2+o_x+\sigma_e d/2,
\]

\[
v_e=s(y-M/2)+M/2+o_y,
\qquad\sigma_L=+1,\ \sigma_R=-1.
\]

全帧另加左眼原点 `0` 或右眼原点 `N`。矩阵次序必须让 `d/2` 处于**缩放之后的输出坐标**，否则实际视差变成 `s d`，调银幕大小时会意外改变深度。

### 8.3 防止单眼边缘截断

中心银幕、每眼水平方向保留至少 `m` 像素额外余量时：

\[
\boxed{sN+|d|+2m\leq N.}\tag{5}
\]

有公共水平平移 `ox` 时，左式还需加 `2|ox|`；垂直方向要求 `sM+2|oy|+2my≤M`。这说明当前铺满画面的 `s=1` 没有容纳非零视差的完整内容空间。

建议验证时统一使用 `s=0.9`：单眼各边先有 96 px 水平余量，`d=24 px` 时最窄边仍为 84 px。保持对照组与实验组的 `s` 相同，避免把尺寸变化误认成视差效果。

边界预算只保证不裁剪，不保证舒适度。不能因为还剩黑边，就继续扩大视差。最终可按可用视差范围预留固定余量，避免拖动距离时通过自动缩放引入意外的大小变化。

统一变换应包含视频、字幕、播放器控件和焦点。否则字幕留在旧深度、银幕移到新深度，会引入频繁的会聚切换和不一致的遮挡。

### 8.4 物理像素、Android 像素和 CSS 像素

实际渲染链至少包含：CSS 坐标 → WebView/View 缓冲区 → Android 合成 → 眼镜输入 → 单眼微显示器。

若单眼 View 缓冲区宽 `W`、最终参考单眼宽 `N`，已确认水平映射是线性全宽缩放，则：

\[
d_{view}=d_{panel}\frac WN,\qquad
f_{x,view}=f_{x,panel}\frac WN.
\]

例如每眼缓冲区宽 960 而映射到 1920，物理 `24 px` 总视差应在 View 中用 `12 px`。使用归一化视差 `η=d/N` 时，直接用 `dview=ηW`。

但这条换算不能解决未知的拉伸、letterbox、旋转或显示裁切。若输入是 `1920×1080` 并按半屏分流，每眼逻辑区域变成 `960×1080`；当前代码会把 WebView 布局成 8:9，不能未经验证就视作 Full-SBS 的等价路径。若需要支持这种输入，必须显式建模水平压缩和最终恢复，并保持源内容正确的 16:9 比例。

`devicePixelRatio` 只描述前端与其绘制环境的关系，不足以独自确定整条外接显示链。新增视差应优先在原生双眼合成层计算；给整个 React 根节点加一次 CSS `translateX()` 会同时移动两眼，视差仍不变。

## 9. 观看感、舒适度与时序

### 9.1 会聚与调焦不能混为一个距离

正常实物观看中，会聚需求和调焦需求通常指向同一位置；固定光学系统的立体显示通过左右图像移动改变会聚刺激，软件不能据此改变实际光学调焦位置。

令 `A=1/Za`，会聚—调焦差值为：

\[
C=\frac1Z-\frac1{Z_a}
=\left(\frac1{Z_0}-\frac1{Z_a}\right)+\frac d{f_xb}.
\]

即使 `d=0`，只要 `Z0≠Za`，也不能断言冲突为零。Shibata 等人的原始研究表明，不适与冲突的大小、正负、基准距离和个体差异有关；它不能简化为全人群统一的“允许偏移屏宽 3%”。[R6]

在取得设备和用户条件后，可把产品限制写成参数化交集：

\[
V\in[V_{min},V_{max}],\quad V>0,
\]

\[
-C_{far}\leq V-A\leq C_{near},\quad
sN+|f_xb(V-V_0)|+2m\leq N.
\]

这些界限是需要验证的产品参数，不是本文凭公式得出的医学阈值。`Za` 未知时，不应假装已计算出个人舒适区。

### 9.2 为什么加了视差，也未必出现强烈“空间感”

一块正对用户的平面，内部所有内容视差相同。尤其在远距离、没有外部参照、角尺寸不变时，绝对距离感可能较弱。会聚刺激改变不等于所有人都会准确感知“3 米”。

诊断时可以加入一个稀疏的零视差参考框，以及一个具有目标视差的小网格。二者的相对会聚差为：

\[
\Delta V=\frac{d_{grid}-d_{frame}}{f_xb}.
\]

这更容易检验深度方向。参考框属于校准图案，日常播放器仍以一块完整银幕为主，避免把所有控件散布到不同深度。

在已配准的平行模型中，固定大小平面整体改变深度还会改变角尺寸，提供与会聚一致的额外线索。应先完成“相同角尺寸下改变视差”的对照，再评估这种组合交互。

### 9.3 不应通过旋转两幅 2D 图来模拟眼睛

未经校准的左右反向 `rotateY()` 会产生梯形失真和边缘错配。对于本次正对用户的平面，优先使用对称平移与统一缩放。

如果以后加入任意姿态银幕，令平面点为 `P(ξ,η)=C+ξa+ηbplane`，应通过两眼各自的 `Ke,Re,Ee` 投影得到单应矩阵，必要时再做镜片畸变映射；不能把两张二维画面随意旋转当作物理投影。

如果以后要求世界固定，银幕还需由逆头部姿态变换到每一帧的眼睛坐标。3DoF 只提供旋转，不能恢复头部平移产生的完整运动视差。本次仍保持随头银幕的现有产品范围。

### 9.4 同一个 video 不等于双眼绝对同步

一个 `<video>`、一个解码器、同一个 `drawingTime` 是良好的架构条件，但 WebView 硬件视频纹理可能由独立的合成路径更新。必须验证左右重放的是同一视频帧，且矩阵同时作用于视频与 DOM。

若运动速度为 `vx` 像素/秒，左右采样时间相差 `Δt`，可能出现额外视差量级：

\[
|d_{temporal}|\approx|v_x\Delta t|.
\]

例如 `960 px/s` 与 `16.7 ms` 会产生约 `16 px` 的误差量级，已经与正常银幕调节量相当。用带帧号、移动竖线的测试视频验收，比静态截图更能排除此类问题。

保留硬件加速与现有持续重绘，先测量再优化。不要用每帧 `WebView.draw(Bitmap)` 加 CPU 回读代替合成：Full-SBS RGBA 图仅按 `3840×1080×4` 计算就约 16.59 MB，每秒处理 60 帧对应约 0.995 GB 的原始数据量，尚未计入额外复制；这不是设备实测带宽，也不代表复用 GPU 图层就必有同等 CPU 开销。

若现有 `drawChild()` 无法同时正确变换视频纹理与 DOM，应在单 WebView、单 HTML video 的约束内验证统一 GPU 合成路径，不能以第二个播放器或第二个 WebView 绕过问题。

## 10. 不猜绝对距离的验证与校准流程

### 10.1 先验证左右眼通道

在原生合成层放无敏感内容的诊断图案：左半屏标 `L`，右半屏标 `R`，并使用不同形状。分别遮住一只眼睛，确认左眼仅见 `L`、右眼仅见 `R`，圆形显示为圆形。

同步记录不含会话的显示信息：命令是否确认、实际模式宽高/刷新率、根 View 宽高、每眼 viewport、映射类型和错误枚举。SDK 回调成功本身不能替代这个验收。

### 10.2 先验证相对视差，再显示米数

保持 `s=0.9`，按最终单眼宽 1920 的归一化比例依次试：

```text
总视差：0 → +8 → +16 → +24 px
单眼偏移：±0、±4、±8、±12 px
```

这些是短时调试阶梯，不是已经验证的长期默认值或舒适上限。开始时使用零偏移，逐级确认单一融合图像及远近方向；出现复视或不适即返回前一可接受档或镜像 2D。

第一轮不默认提供负视差“无限推远”：若实际 `Z0` 已接近无穷远，负视差会要求发散。基准校准以后，才开放有明确下界的远端范围。

未知 `Z0` 时，设置文案采用“基准 / 靠近程度”和独立“银幕大小”。有标定依据后，再用米显示估算距离。这是先完成可用控制、再获得绝对量纲的实施路径，不妨碍现在开始修复。

### 10.3 估算绝对距离映射

若设备允许透视真实目标，可在固定佩戴、已知目标距离 `Z1,Z2,…` 下，以匹配标记调节图像视差 `d1,d2,…`。优先逐眼对齐虚拟标记与同一真实目标，再双眼复核；仅问“感觉多远”会有较大偏差。看不清真实目标时，不可把黑背景上的主观远近感当作光学测量。

拟合：

\[
d_i=\frac{a}{Z_i}+c,\qquad a\approx f_xb,\quad c\approx-a/Z_0.
\]

只有两个点时：

\[
a=\frac{d_1-d_2}{1/Z_1-1/Z_2},\qquad
c=d_1-a/Z_1.
\]

若 `a>0,c<0`，则 `Z0=-a/c`；`c≈0` 对应近似无穷远。`a≤0` 提示眼序/符号或数据问题；`c>0` 提示当前零参考可能指向发散，不能强行解释为正的 `Z0`。

多个距离应做最小二乘并检查残差、重复佩戴后的变化。用像素到光线的光学标定设备测量可以进一步提高可靠性。以上流程不能测得 `Za`；调焦距离需要独立光学依据。

拟合后可直接用 `Z=a/(d-c)`，因此只做中心远近控制时，未必需要单独获得精确的 `fx` 和 `b`。但这仍是当前佩戴条件下的标定模型，不应跨设备型号、固件和用户盲目复用。

## 11. 对应到项目的修改设计

### 11.1 分阶段实施

| 阶段 | 修改位置 | 可检查的交付条件 |
| --- | --- | --- |
| A：识别通路 | `GlassesPresentationController`、显示状态发布、诊断图 | 眼序、比例、实际几何与命令确认可分别判断 |
| B：修复视差 | 新增纯数学几何类；`StereoMirrorLayout.dispatchDraw()` | 左右位移为 `±d/2`；缩放和视差独立；边缘预算成立 |
| C：提供设置 | 原生偏好/有界桥、`CompanionUI/src/App.jsx` | 远近与大小可调；未标定时不显示伪精确米数 |
| D：接入校准 | 设备/佩戴标定配置 | 使用有效 `a,c` 或 `fx,b,Z0`，限定前方可行距离 |
| E：完善体验 | 文案、文档、短时平滑、真机播放验收 | 字幕、控件、视频同平面且双眼同步；模式失败恢复可见 2D |

不为距离调节重复调用 `switchTo3DMode()`：硬件进入已确认的 SBS 后，拖动滑杆只更新几何参数。

### 11.2 纯数学类的边界

建议新增 `StereoScreenGeometry`，不依赖 Activity、Canvas、会话或 Jellyfin，输入经过验证的显示几何与设置，输出两个 viewport 和变换：

```text
DeviceGeometry
    perEyeViewportWidth/Height
    sourceWidth/Height
    mappingVerified
    calibration: unknown | calibrated
    calibrated parameters (optional)

ScreenSettings
    normalizedDisparity             // 未标定时
    targetInverseDistance          // 已标定时，二者只取一种
    sizeFraction

GeometryResult
    leftViewport, rightViewport
    leftTransform, rightTransform
    effectiveDisparity, effectiveScale
    validationStatus
```

验证 NaN、Infinity、非正尺寸、奇数总宽度的分区规则、越界视差及裁剪预算。无法识别的显示映射不能依靠“总宽度除二”就声称成功。若要表达无穷远，用距离倒数 0，而不把 Infinity 穿过 JSON 桥。

设置通过有固定大小、范围和枚举的消息进入原生层；持久化偏好只保留一份权威来源，前端接收状态快照。新增瞳距等个人校准值若使用，应保留本地，不进入通用分享诊断。

### 11.3 可直接指导原生绘制修改的伪代码

以下假设已验证 Full-SBS 等比映射，源 WebView 为 `W×H`。这是设计伪代码，不是已经合并或通过真机验证的实现：

```java
// d: View 输出坐标中的总视差，正值表示相对靠近。
// s: 统一尺寸比例。满足 s * W + abs(d) + 2 * margin <= W。
float dx = (W - s * W) * 0.5f;
float dy = (H - s * H) * 0.5f;

int leftSave = canvas.save();
canvas.clipRect(0, 0, W, H);
canvas.translate(dx + d * 0.5f, dy);
canvas.scale(s, s);
drawChild(canvas, child, drawingTime);
canvas.restoreToCount(leftSave);

int rightSave = canvas.save();
canvas.translate(W, 0f);
canvas.clipRect(0, 0, W, H);
canvas.translate(dx - d * 0.5f, dy);
canvas.scale(s, s);
drawChild(canvas, child, drawingTime);
canvas.restoreToCount(rightSave);
```

实现要点：

- 先固定各眼 viewport 的裁剪，再做内容平移和缩放，防止图像跨入另一只眼。
- 黑色背景覆盖整个输出；检查局部脏区刷新时不会留下旧偏移残影。
- 调整距离时保持 WebView 的布局尺寸，不触发 CSS 响应式重排、视频重建或播放会话重启。
- `d` 与 `s` 使用同一帧状态快照；切换模式时清除过期动画。
- 有远近动画时，对 `V=1/Z` 或等价 `d` 插值；例如 `V(t)=Vstart+(Vtarget−Vstart)(3q²−2q³)`，`q=clamp(t/T,0,1)`，避免以米做线性变化导致视差速度不均匀。`T` 由交互实测选择。
- 镜像恢复时清除视差并恢复其全画面布局，保证看见有效 2D。

### 11.4 模式状态与几何状态的衔接

现有状态机能处理命令拒绝和超时，应保留其“失败可见 2D、停止自动重试”的约束。补充区分“硬件已确认”与“几何映射已验证”；新硬件模式若同时触发 Display 改变，需要在当前显示上刷新几何信息。

`GlassesPresentationController.refreshDisplay()` 约 140 行在 display ID 不变时直接返回。这不等于 Android 一定不会重新布局，但目前没有明确更新模式几何的逻辑；后续必须覆盖“同 ID 分辨率变化”的通知与参数刷新。

不能为等待校准、等待普通参数更新长期隐藏 WebView。若等待几何属于同一硬件切换，则纳入有界切换时间；若超时或几何不支持，结束切换、请求安全 2D 并恢复可见内容，不制造新的黑屏等待态或自动重试循环。

## 12. 可证伪的验收标准

### 12.1 数学与图像验收

| 对照或检查 | 应观察到什么 | 不符合时优先检查 |
| --- | --- | --- |
| 单眼遮挡读 L/R | 两眼只见自己的标记 | 硬件分流、眼序、回调与实际模式 |
| 圆形、方格、角点 | 正确纵横比，四角完整 | 输入几何、Android 缩放、裁切 |
| `d=0`、固定 `s` | 两个局部图像位置一致 | 额外平移、viewport 原点 |
| `d=16`、固定 `s` | 左中心 `+8`，右中心 `−8` | 符号、每眼/总视差混淆 |
| 只改 `s` | 对应点总视差保持设定值 | 错误变换次序把 `d` 乘了 `s` |
| 只改 `d` | 大小相同，平均中心不移动 | 单边平移、额外缩放 |
| 角点和字幕最远边界 | 两眼都完整，没有跨眼渗入 | 式 (5)、clip 次序和残影 |
| 移动帧号视频 | 左右同帧，DOM 与视频位移一致 | WebView 视频合成路径、帧时序 |
| 相对深度参考图 | 目标随正视差增加而相对靠近 | 配准、融合、眼序、基准模型 |

合成图像的对应点应按已知变换做配准后比较，排除文字抗锯齿、采样边缘与黑边影响。理想 `dv=0`；可用“最终输出像素中垂直残差不超过 1 px”作为初始图像检查容差，不把它解释为生理安全阈值。

纯数学检查至少覆盖：`Z=Z0 → d=0`；`Z` 减小时 `d` 增大；视差到距离的往返；视差与缩放独立；左右平均中心稳定；分辨率等比变化时归一化视差不变；禁止发散目标；非法数值和裁剪边界。

### 12.2 设备与项目验收

实施阶段遵循 [Android 架构回归矩阵](ANDROID_ARCHITECTURE.md#device-regression-matrix)，至少覆盖：

- 已连接/后连接、拔插、同 ID 模式尺寸变化、前后台和 Activity 重建。
- 正常 2D/SBS 切换、拒绝、异常、缺回调与超时，所有失败均可见 2D。
- 浏览、字幕、seek、暂停/继续、换集、音轨和文字/烧录字幕。
- 一个眼镜 WebView、一个 HTML video、一个声音流、一次播放上报。
- Renderer 恢复、登录退出和会话过期后清理。
- 对应硬件 MediaCodec、实际刷新率、双眼时序与合成负担。

涉及 WebView/桥接的实际代码提交，需完成 GlassesUI 类型检查、两套前端生产构建、JVM 测试、Android lint、APK 组装和 `scripts/verify-no-unity.sh`，并有真机矩阵记录。分析阶段只新增本文；后续实现验证记录在第 14 节。

### 12.3 建模阶段完成的验证

读取并定位了原生布局、显示控制、状态机与相关前端文案；核验官方 SDK 下载包 MD5；检查 `AirApi` 的方法委托；用 Python 独立复算视场、视差、角度和数量级。

建模阶段尚未取得 Air 3s 实测眼序、光学基准、有效显示映射或佩戴结果。后续第 15 节补充了眼序、输出映射和相对远近感的真机证据；绝对光学距离仍未标定。

## 15. 真机排查与中间方案（2026-09-06，服务依赖已移除）

本节保留故障来源和视差实测证据。排查曾借助已安装的官方控制服务切换硬件，但该中间方案引入了不应存在的 XR 空间运行依赖。用户明确要求软件独立运行后，服务绑定、启动入口、版本绑定和旧 SDK 均被移除，详见第 16 节。

### 15.1 为什么调参后仍像镜像 2D

测试组合为 RayNeo Air 3s、小米 Android 16 手机、已安装的雷鸟 XR 空间 2.1.1（versionCode `260702140`）。原 Air SDK 1.0.3 的模式调用发送旧协议命令 6/7，但该版本的 `ArService` 仅把它们转为 `com.tcl.xr.game.state.open` / `close` 广播，未执行硬件模式切换，也没有旧式模式回执。因此，即使加入了正确的视差绘制，眼镜仍可能停留在 1920×1080；应用不能将“选择了虚拟银幕”当作“已经生效”。

通过已安装官方客户端和服务端的静态反汇编相互核对，确定真正调用眼镜 2D/3D 控制函数的导出 `MonitorService` 路径，再在设备上验证分辨率变化。仓库只实现两个模式命令，未复制厂商二进制。这是对一个明确版本的内部兼容实现，不是雷鸟新发布的公开 SDK，也不能据此承诺其他版本兼容。

| 固定契约 | 验证值 |
| --- | --- |
| 服务 | `com.tcl.xrmanager.main/com.ffalcon.xr.server.service.MonitorService` |
| Binder descriptor | `com.ffalcon.xr.sdk.IFFalconXrTube` |
| Binder transaction | 1，oneway；接口 token、存在标志 1、socketpair 的远端文件描述符 |
| 控制帧 | 固定 72 字节、小端；偏移 0 为 int32 功能号，偏移 4/8 为调用者 UID/PID，其他字段为零 |
| 功能号 | 4：2D；5：3D |
| 控制库 | `lib/arm64-v8a/libFFalconXRServer.so`，795896 字节 |
| SHA-256 | `45a8284cb371ed76cc51ccfdb83217117e3e07fdf1be4024c91f3bd36d8c8200` |

在后台单线程、有界队列中核验版本与控制库，使用非阻塞 socket 写入，过期请求不执行。未知版本、二进制或接口描述符不匹配时停止发送。该通路没有模式确认回包；实际确认来自命令已写入后观测到的物理 `Display.Mode` 和 Presentation 几何，不能把 IPC 成功误报为眼镜成功。

旧设备仍保留 AirApi 通路，并修正旧回调 boolean 的语义：它表示切换后的 stereo 状态，2D 的正确回执为 `false`。所有切换共享 8 秒截止时间；失败结束遮罩并只请求一次安全 2D，不形成自动重试循环。

### 15.3 Android 16 外接显示限制与窗口保留

这台手机在真实 2D/SBS 切换时因 EDID 改变移除并重建外接逻辑显示，而且重建后 `mIsEnabled=false`。普通 `DisplayManager.getDisplays()` 不再返回该眼镜，外接画面由系统关闭。这与视差公式或“参数有没有保存”是不同的问题。

实现保留有效的暂时 OFF 眼镜候选，在当前有界切换内保留唯一 WebView，并可将它挂载到重新创建的 Presentation；同 ID 尺寸变化会重新读取几何，旧窗口回调不会覆盖新输出。另通过只读显示分类识别“系统尚未启用眼镜输出”，在首页及设置展示，与当前实际模式和偏好分开。

前期恢复外接显示使用了 ADB 的 `cmd display enable-display <眼镜逻辑ID>`，仅启用已连接的眼镜，没有改动全局安全或电源设置。用户随后明确说明：HyperOS 连接眼镜后需要手动开启系统「屏幕镜像」，否则不允许向眼镜输出。这修正了前期对恢复路径的判断；XR 空间启动失败是引入额外依赖造成的独立问题，不能用它解释 HyperOS 的系统开关。应用的 2D 回退不能代替用户开启系统镜像。

## 16. 移除 XR 空间依赖：直接控制 USB（2026-09-06）

### 16.1 当前运行边界

0.2.2 将硬件控制改为本应用通过 Android `UsbManager` / `UsbRequest` 直接访问 Air 3s。移除了 XR 空间 `MonitorService`、Binder/socket IPC、包查询、打开其他应用的桥方法及 UI 按钮。旧 Air SDK AAR 不再参与编译或进入 APK，构建脚本不再下载它。历史下载脚本仅保留为第 1–13 节分析的复核辅助。

显示仍使用唯一 WebView 和 `<video>`，之前验证过的视差、缩放、裁剪公式不变。系统「屏幕镜像」决定 HyperOS 是否允许外接显示输出；本应用的 Mirror 2D/SBS 选择决定眼镜通道模式与内容几何，二者不混淆。

### 16.2 可追溯的最小 USB 协议

沿第 15 节已取得的官方服务库继续静态核对，得到以下最小契约。库只作为协议证据保存在临时目录；实现没有装载或复制其代码、算法或二进制。

| 核对对象 | 证据 |
| --- | --- |
| `XRService::SwitchTo3D`，地址 `0x5a308` | 调用 `SendHidCommand`，功能号 6，子命令 0，空参数 |
| `XRService::SwitchTo2D`，地址 `0x5a434` | 同路径，功能号 7，子命令 0，空参数 |
| `XRUsbController::SendCommand`，地址 `0xa22b4` | 清零 64 字节；首字节为 `0x66`；向输出端点发送完整报告 |
| 填充回调，地址 `0xa30a4` | 功能号放在偏移 1，子命令放在偏移 2，参数从偏移 3 起 |
| 真机 USB 描述 | VID/PID `1bbb:af50`；接口 0，HID 3/0/0；OUT `0x01`、IN `0x81`，interrupt，最大包 64 字节 |

因此当前只允许两个固定包：`66 06 00…00` 和 `66 07 00…00`，均为 64 字节。它们与第 15 节的 72 字节进程间消息不是同一层协议。实现核对上述设备和端点身份，其他身份停止发送；没有添加固件写入、USB 重置、任意控制包或 WebView 字节接口。

传输在单线程有界队列中执行，等待最多 750 ms，结束立即释放所占 HID 接口。Android USB 权限归本应用所有，不借用其他应用授权。授权等待不会遮黑眼镜、不占用 8 秒硬件切换窗口；拒绝后不在恢复前台时自动重弹。

### 16.3 HyperOS 连接与确认流程

首次 Presentation 测量后才决定是否发命令。如果物理/窗口输出已经符合请求模式，直接确认使用，避免用户开启系统镜像后再次触发 EDID 重连。需要改变模式时，先获得本应用 USB 权限，发一次命令，再以实际输出确认。只有写入成功仍不能宣布 SBS 生效。

HyperOS 暂未允许外接显示时，首页和设置明确提示在手机系统中开启「屏幕镜像」。应用不替用户修改该系统开关，不跳转 XR 空间，也不会在系统关闭输出时反复发送模式命令。用户返回后重新读取显示状态。超过有界切换窗口则结束过渡，待系统输出恢复后再应用所选模式。

## 17. 切换后画面缩小与视口裁切修复（2026-09-06）

### 17.1 两层坐标必须一致

真机复现了 SBS 切回 Mirror 2D 后，1920×1080 输出中只有左上角约 852×480 存在画面的故障。切换前外接显示密度为 213 dpi，重建后 WebView 的 JS 读数落到手机的 480 dpi。缩小比例与 `213/480 = 0.44375` 相符。原生窗口尺寸正确、DOM/video 对象不变，并不足以证明内容正确绘制。

0.2.3 尝试通过 `MutableContextWrapper` 更新 Presentation 上下文并派发配置变化，真机仍失败。Chromium 的 `AwContents` / `WindowAndroid` 保留内部显示对象，简单更换 Android Context 基类无法保证这些缓存同步。最终改为使用手机 Activity 的稳定渲染上下文创建唯一 WebView；外接 Presentation 仍负责窗口、原生像素布局和双眼 Canvas 变换。

只做这一步还会遇到第二个问题：`width=device-width, initial-scale=1` 与页面的最小宽度 1024 CSS px 冲突。手机密度为 3 时，1920 原生像素仅对应 640 CSS px 的可见宽度，页面右侧和底部被裁切。最终将眼镜页面视口设为 `width=1440`，取消固定初始缩放，让 WebView 的 overview fitting 完整适配。

设单眼源 View 宽度为 `N`，高度为 `H`，稳定渲染密度为 `ρ`，页面设计宽度 `C=1440`，浏览器页面缩放为 `z`，则完整适配要求：

```text
z = N / (ρ C)
CSS 到原生像素比例 = ρ z = N / C
CSS 视口高度 = H C / N
```

本机 `N=1920, H=1080, ρ=3`，因此 `z=4/9`，页面、可见视口和视频均为 **1440×810 CSS px**，对应完整 1920×1080 源 View。之后才应用第 14 节的双眼缩放与 ±d/2 位移。这使手机密度、页面适配和眼镜视差各自有明确坐标单位。此实现中 JS 的 `screen.*` 可以继续反映手机；实际眼镜模式始终由原生输出确认。

Chromium 实现核对来源：[AwContents.java](https://github.com/chromium/chromium/blob/main/android_webview/java/src/org/chromium/android_webview/AwContents.java)、[WindowAndroid.java](https://github.com/chromium/chromium/blob/main/ui/android/java/src/org/chromium/ui/base/WindowAndroid.java)。它们用于解释缓存行为，最终验收以本机实际输出为准。
